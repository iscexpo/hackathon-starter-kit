# Participant Guide

Welcome! This guide is designed to help teams move from a real problem to a small, demonstrable prototype. The event organizer must publish the event's actual dates, eligibility, team-size limits, tracks, and rules in `EVENT_CONFIG.md` or the official event page.

## 1. Before the event

- Read the published rules, schedule, submission deadline, code of conduct, and judging criteria.
- Form a team within the event's team-size rules, or use the organizer's team-matching process if offered.
- Choose a problem you can explain clearly and test within the available time.
- Check that datasets, APIs, design assets, and libraries can be used for your project.
- Bring a backup plan in case Wi-Fi, a service, or a deployment fails.

## 2. During the hackathon

### Understand the problem

Write one or two sentences describing who has the problem, what they struggle with, and how you know it matters. Avoid trying to solve every part of a large problem.

### Define the smallest useful solution

Choose a minimum viable prototype with a few working features. Agree on what the team will not build during the event.

### Build in small steps

1. Create the repository and assign tasks.
2. Make a simple end-to-end path work before polishing extras.
3. Commit often and keep the project runnable.
4. Test the main user journey with someone who did not build it.
5. Keep a record of trade-offs, data sources, and tool usage.

### Ask for help well

Explain what you expected, what happened, the smallest steps to reproduce it, and what you already tried. Do not share tokens, private data, or credentials in a public channel.

## 3. Prepare the demo

A good demo should show the problem, the working flow, and the value in a short amount of time. Have a backup recording or screenshots if the event permits them. Explain what is implemented and what is only a mockup; never imply unfinished features are working.

## 4. Submit on time

Follow the official submission channel and deadline in the event configuration. Complete [`SUBMISSION.md`](../SUBMISSION.md), check your repository permissions, test setup steps, and confirm links work for judges. A submission is not complete until the event's required form or portal confirms receipt.

## 5. Responsible building

- Use data you have permission to use; do not expose personal or sensitive data.
- Do not test against systems without authorization.
- Be transparent about AI-assisted tools and third-party code according to the event rules.
- Attribute adapted material and check software/data licenses.
- Design for inclusion: use readable text, keyboard-accessible controls, captions where relevant, and plain-language explanations.
- Treat teammates, mentors, judges, and other teams respectfully.

## 6. After the event

Respect any publication or prize conditions. Fix exposed secrets immediately and notify the organizer privately if a sensitive item was published. If you continue the project, document known limitations and how users can report issues.
